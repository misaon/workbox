# 0005. Oxlint and Oxfmt, Turborepo boundaries instead of ESLint

- Status: accepted
- Date: 2026-09-30

## Context

The owner wants the strictest, fastest linting available. TypeScript 7 exposes no JavaScript API, and `@typescript-eslint/parser` requires one ([R10 §3, §6](../superpowers/research/2026-09-30-R10-toolchain-config-reference.md)).

## Decision

**Linter.** Oxlint 1.86 with type-aware rules through `oxlint-tsgolint`, run as `oxlint --type-aware --deny-warnings`. The categories `correctness`, `suspicious`, `pedantic`, `perf` and `style` are at `error`. The `restriction` category is off, because it bans language and library features wholesale; the restriction rules the project wants are enabled one by one at `error`. Nothing is at `warn`, so `--deny-warnings` only guards a future `warn` setting. Plugins: `typescript`, `unicorn`, `oxc`, `import`, `promise` and `node` everywhere; `jest` for test files; `react` and `jsx-a11y` for `apps/web`; `vitest` for the web client's test files.

**Formatter.** Oxfmt 0.71 is the only formatter. It covers every source and configuration file type in the repository (TypeScript, JSON, YAML, Markdown, CSS, HTML), and its `sortImports` owns import order. There is no Prettier and no ESLint.

**Dependency rules.** Every package declares one Turborepo tag in its `turbo.json`, and the root `turbo.json` defines nine tags: `protocol`, `i18n`, `observability`, `core`, `adapter`, `sim`, `render`, `app-web` and `app-cli`. Their deny lists encode the dependency rules of spec §4.3: `protocol` depends on no internal package; `i18n`, `observability`, `core` and `sim` only on `protocol`; `adapter` on `core`, `protocol`, `observability` and `i18n`, never on another adapter; `render` on `protocol`, `sim` and `i18n`; `app-web` on `protocol`, `sim`, `render` and `i18n`; `app-cli` on everything. `pnpm boundaries` (`turbo boundaries`) enforces them in CI. Only `protocol`, `i18n`, `observability`, `app-web` and `app-cli` have packages today; the other tags govern packages before they exist.

**Runtime purity of leaf packages.** `packages/protocol/.oxlintrc.json` bans the `Bun` and `process` globals and imports of `bun:*` and `node:*`, so the protocol package stays runtime-neutral; the import ban is lifted for its `test/**`.

**Nested configuration.** Oxlint applies the nearest `.oxlintrc.json` to a file, and a nested file does not merge with the root one, so every nested `.oxlintrc.json` must `extends` the root. A nested file without `extends` silently stopped reporting `no-console` in a probe. Today only `packages/protocol` has one.

**Suppressions.** A disable comment states its reason: `// oxlint-disable-next-line <rule> -- <reason>`. The colon form (`<rule>: <reason>`) suppresses nothing in Oxlint 1.86, and Oxlint cannot check that a reason is present, so the rule is enforced in review ([CONTRIBUTING.md](../../CONTRIBUTING.md)). A rule that cannot apply to a whole class of files is configured in `.oxlintrc.json` and listed below instead of being suppressed line by line.

**Tests under `bun:test`.** `jest/no-focused-tests` and `jest/no-disabled-tests` do not flag `.only` and `.skip` in suites that import from `bun:test` (the same code with globals or `@jest/globals` is flagged). Test files therefore also enable `no-restricted-properties` for `only` and `skip` on `describe`, `it` and `test`. The aliases `xdescribe`, `xit` and `xtest`, `.todo` and `.skipIf` are not covered; the gated binary test uses `describe.skipIf` on purpose.

**Rule ledger.** JSON configuration carries no comments here, so this table is the record of every rule that differs from its category default; every other rule of an enabled category and plugin is at `error`. Categories are Oxlint 1.86's own (`oxlint --rules -f json`). The states are `opt-in` (a restriction rule enabled at `error`), `off`, `reconfigured` (still enforced, with other options), `test-only` (off in `*.test.ts` and `*.test.tsx` only) and `scoped` (enabled for part of the tree only); a scope in parentheses means the row does not apply everywhere.

## Consequences

A change to a rule's level or options in `.oxlintrc.json` updates the ledger in the same pull request. Oxfmt is a 0.x release and there is no Prettier fallback, because Oxfmt covers every file type here. If ESLint-only plugins become necessary, they need a TypeScript 6 alias in a separate workspace.
