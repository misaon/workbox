# R5 — Sandboxing / isolation options for AI coding agents (Sept 2026)

Status: research draft, 2026-09-30. All claims below were checked online on 2026-09-30 against the sources in section 6. Items marked **[unverified]** could not be confirmed from a primary source; **[3rd-party]** means only a non-official source was found.

## 1) Summary of findings

1. **The market has converged on three local isolation tiers**: (a) OS-level process sandboxes (macOS Seatbelt via `sandbox-exec`, Linux bubblewrap ± Landlock/seccomp) that ship *inside* both Claude Code and Codex; (b) shared-kernel OCI containers (Docker Engine/OrbStack/Podman, devcontainers); (c) per-session microVMs with their own kernel (Docker Sandboxes `sbx`, Apple `container`). Cloud sandboxes (E2B, Modal, Cloudflare, Vercel, Fly Sprites, Docker Cloud Sandboxes) are all microVM/gVisor based and metered per second.
2. **Docker Sandboxes is the strongest local option and needs no Docker Desktop.** The `sbx` CLI is a free, standalone product (free "including for commercial and professional work"); local sandboxes run on macOS 14+/Apple silicon, Windows 11 (WHP) and now Ubuntu 24.04+ with KVM. Each sandbox is a microVM with a private Docker daemon; credentials are injected by a host-side proxy so "the raw credential values never enter the VM". Docker Cloud Sandboxes went GA on 2026-09-24 ($0.07–1.12/h, `sbx move --to cloud`). Costs: a real VM per session (defaults to 50% of host RAM, max 32 GiB, per third-party CLI dump) and a reported "crippling" I/O penalty on mounted workspaces; the docs' clone mode avoids the mount.
3. **Anthropic's `@anthropic-ai/sandbox-runtime` (srt) is stable enough to build on but still labelled "Beta Research Preview"** (v0.0.78 published 2026-09-30, Apache-2.0, Node ≥20.11, Windows alpha). It is the same engine behind Claude Code's `/sandbox`; Claude Code's built-in sandbox only wraps Bash commands, whereas `npx @anthropic-ai/sandbox-runtime claude` wraps the whole process including MCP servers and hooks — Anthropic's documented minimum for `--dangerously-skip-permissions` runs without Docker.
4. **Codex CLI sandboxes by default** (read-only / workspace-write / danger-full-access). Current docs say Linux/WSL2 uses **bubblewrap** (first `bwrap` on PATH, else a bundled helper; needs unprivileged user namespaces) with Landlock/seccomp layered underneath per a Sept-2026 comparison; Nov-2025 analyses described Landlock+seccomp only, so the backend changed during 2026.
5. **Credentials are the architectural constraint, not isolation.** Anthropic's legal page: OAuth login is "intended exclusively" for subscribers using Claude Code and native apps; developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow", but an end user may sign in "to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code". Third-party harnesses were cut off from Pro/Max OAuth on 2026-04-04. Codex's docs *do* sanction copying `auth.json` to trusted private runners and offer `codex login --device-auth`.
6. **Git worktrees are the de-facto standard for parallel sessions** (Claude Code `--worktree`, Conductor, Vibe Kanban, Paseo, container-use). Claude Code now enforces worktree isolation with four tool-level checks and offers `.worktreeinclude`, `worktree.baseRef`, and `WorktreeCreate/Remove` hooks. Worktrees inside containers/VMs need the shared `.git` common dir mounted (devcontainer CLI 0.81.0 added exactly that) — or use a clone.
7. **Apple `container` 1.0.0 (2026-06-09) is real but narrow**: one VM per container, default 1 GiB RAM/4 vCPU, virtiofs bind mounts, `container machine` persistent Linux environments, K8s plugin, Apache-2.0; Apple silicon only, macOS 26 officially supported, no compose, isolated networks need macOS 26. Firecracker/gVisor/Kata remain Linux+KVM only, so the M4 laptop cannot reuse the server-side stack.

## 3) Credential and git-isolation notes

**Claude Code.** macOS stores the OAuth login in the login Keychain (service `Claude Code-credentials`); Linux uses `~/.claude/.credentials.json` (0600); `CLAUDE_CONFIG_DIR` relocates both and keys the Keychain entry. Precedence: cloud provider → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `apiKeyHelper` → `CLAUDE_CODE_OAUTH_TOKEN` → profile → `/login`. `claude setup-token` mints a one-year subscription token that "can only make model requests"; a Feb-2026 issue shows such tokens are rejected for direct API calls. Inside a container the Keychain is unreachable; the official devcontainer guidance is: mount a named volume at `~/.claude`, set `CLAUDE_CONFIG_DIR` to it, then run `/login` (paste-code fallback works without a callback port). Docker Sandboxes does the same (`/login` inside the VM) while the proxy keeps the token on the host. Given the legal wording, **Workbox should never read the Keychain or copy tokens itself**; either run the agent as a host process (OS sandbox) or give each sandbox its own persistent config volume and let the user complete Anthropic's flow. `CLAUDE_CODE_OAUTH_TOKEN` is safe to *support* (user-provided env) but should not be the default.

**Codex.** `auth.json` lives in `CODEX_HOME` (default `~/.codex`); `cli_auth_credentials_store` = `file|keyring|auto|ephemeral`. Headless: `codex login --device-auth` (beta). OpenAI's CI/CD page permits seeding `auth.json` on a trusted private runner and letting Codex refresh it (~8-day staleness), one file per runner, never shared concurrently — a per-sandbox `CODEX_HOME` volume is compliant; OpenAI still recommends API keys for programmatic use.

**Egress and secrets.** Every serious option is deny-by-default with a domain allowlist and a proxy that injects credentials: srt/Claude (`allowedDomains`, `strictAllowlist`, `credentials.mask` + `tlsTerminate`, SigV4 re-signing), Docker `sbx` (host proxy, sentinel values, SSH-agent forwarding by default, UDP/ICMP blocked). Minimum allowlist for Claude: `api.anthropic.com`, `claude.ai`, `platform.claude.com`. Known gaps common to all: an allowed `github.com` still permits exfiltration by push; a mounted `docker.sock` or writable shell rc/`.git/hooks` is a host escape (srt blocks the latter automatically).

**Git isolation.** *Worktrees* (Claude Code default: `.claude/worktrees/<name>`, branch `worktree-<name>`, `baseRef` fresh|head) share the object store and are created in seconds; Claude Code blocks edits, `cd`, `git -C/--git-dir/GIT_DIR` and unparsable commands that reach the main checkout, holds `git worktree lock` while running, and skips repo-local filter drivers (LFS) because they are shell commands. Hazards: shared `.git/config` and hooks, untracked files (`.worktreeinclude`), per-worktree `node_modules`, and the `.git` *pointer file* which breaks when only the worktree is mounted into a VM (Docker docs: agent "has no Git access"). *Fresh clones* (Docker clone mode: source read-only at `/run/sandbox/source`, results fetched via a `sandbox-<name>` remote) give the strongest isolation at disk/time cost. *Bind-mounted repos* (direct mode) make edits live on the host and let hooks/Makefiles/CI configs execute host-side — acceptable only with OS sandboxing. Conductor (v0.89.1, macOS, worktree per workspace, copies tracked files only), Vibe Kanban (community-maintained, fully local since bloop's 2026-04-10 shutdown), Paseo (Apache-2.0, `--worktree`, reuses host CLI logins, optional Docker) and Cursor cloud agents (VM per agent, clone from Git host, secrets injected at start) all follow the worktree-or-clone pattern.

## 4) Recommendation

Define a small `SandboxProvider` interface in TypeScript:

```ts
interface SandboxProvider {
  capabilities(): { kernelIsolation: 'none'|'os'|'container'|'vm'; nestedDocker: boolean; hostMounts: boolean; persistentVolumes: boolean };
  create(spec: { workspace: WorkspaceSource /* worktree|clone|mount */; agent: 'claude'|'codex'|...; configDir: string; network: EgressPolicy; resources?: {cpus?: number; memoryMiB?: number}; env: Record<string,string> }): Promise<Sandbox>;
}
interface Sandbox { exec(cmd, opts): Child; attachPty(cmd): Pty; readFile/writeFile; forwardPort(port); snapshot?(): Promise<Id>; destroy(): Promise<void>; }
```

Implement in this order:

1. **`local-os` (default, ship first)** — spawn the unmodified agent CLI on the host under srt (`SandboxManager.wrapWithSandbox`), one git worktree per session, allowlist = agent endpoints + package registries, `denyRead` for `~/.ssh`, cloud creds, other projects. Zero install on macOS, `bubblewrap socat` on Linux; credentials never leave the user's Keychain/`~/.codex`; matches Anthropic's stated minimum for unattended runs. Also set Claude's `/sandbox` strict mode and Codex `workspace-write` inside it for defense in depth. Open question: nested Seatbelt profiles (srt outside, Claude's Bash sandbox inside) on macOS.
2. **`microvm-sbx`** — wrap the `sbx` CLI (`sbx run|create|exec`, `--clone`, `--memory`, `sbxenv.yaml`, `sbx policy`). Use clone mode, explicit `--memory 3g --cpus 2` per sandbox, per-sandbox persistent `CLAUDE_CONFIG_DIR`/`CODEX_HOME` volumes with in-sandbox `/login`. Detect `sbx` absence and offer a one-line install. Later maps 1:1 to Docker Cloud Sandboxes and to Linux servers with KVM.
3. **`oci`** — Docker Engine API (dockerode) against whatever runtime exists (OrbStack/Colima/Podman/Docker Desktop; Apple `container` via CLI adapter later), devcontainer.json-aware, worktree common-dir mounted, Anthropic's default-deny iptables script optional. For users who need reproducible toolchains.
4. **`remote`** — SSH to a Linux host running provider 1 or 3; then cloud adapters (Fly Sprites for persistent workspaces, E2B/Modal for ephemeral) behind the same interface.

Best default for a one-command install without Docker: **`local-os` + worktrees**, with Workbox surfacing a "harden this session" action that upgrades to `sbx` when installed.

## 5) Open questions for the owner

1. Is copying the user's own Claude OAuth token into a Workbox-managed sandbox acceptable under the "may not collect, store, or intermediate" clause, or do we insist on in-sandbox `/login`? (Recommend the latter; ask Anthropic sales if unsure.)
2. Does srt's Seatbelt profile leave Keychain/`securityd` reachable so an OS-sandboxed `claude` can refresh its token? Needs a spike.
3. Acceptable per-session RAM budget on the M4 (drives `sbx --memory` default and whether 5 parallel microVMs are realistic on 24–48 GB).
4. Direct-mount vs clone mode as Workbox default for `sbx` (live edits in the IDE vs. I/O penalty and host-hook risk).
5. Should Workbox depend on Apple `container` at all before compose/Docker-API parity, or treat it as an optional `oci` backend?
6. Is the tool commercial (affects Docker Desktop and OrbStack licensing for users)?
